**Task:** given a failure (Defects4J: bug report + failing tests) or a fix (DPDK), rank the earlier commits by how likely each one introduced the bug. Bugs are processed in chronological order; each bug is ranked before its label is revealed (prequential), and learned methods only ever train on earlier bugs. Acc@k = share of bugs whose BIC is in the top k; MRR = mean reciprocal rank (0 when the BIC is outside the candidates); mean rank over bugs whose BIC is a candidate. ΔMRR: paired bootstrap over bugs, 95% CI.

## Methods

- `recency` (baseline): most recent commit first. Inputs: commit order.
- `file-overlap` (baseline): number of touched files named in the stack trace or the report (ties: newest first). Inputs: stack trace, report, files.
- `bm25-diff` (baseline): BM25(report + failure text, commit diff + paths). Inputs: report, failure text, diff.
- `bm25-msg` (baseline): BM25(report + failure text, commit message). Inputs: report, failure text, message.
- `bug2commit (released)` (published): Bug2Commit's released per-bug ranking (Murali et al. 2021, as run by the FONTE authors), re-scored on these candidates. Inputs: report, failing-test symptoms, commit message/files (unsupervised).
- `fbl-bert (released)` (published): FBL-BERT's released per-bug ranking (Ciborowska & Damevski 2022), re-scored on these candidates. Inputs: report, commit diffs; model fine-tuned on external JDT data.
- `linear+tuned` (learned): weighted sum of within-bug z-scored signals (pos_log, bm25_diff, bm25_msg, trace_src, trace_meth, report_files, lines_log), weights in {0, .5, 1} per signal picked by follow-the-leader. Inputs: report text, failing tests (names, exceptions, stack traces), commit time/order, message, diff, files, size, author.
- `logreg` (learned): logistic regression (L2, C=1) over every numeric signal + one-hot features, retrained on all bugs seen so far every 1 bug(s). Inputs: report text, failing tests (names, exceptions, stack traces), commit time/order, message, diff, files, size, author.
- `logreg+tuned` (learned): logistic regression, C in {1, 0.1} picked by follow-the-leader. Inputs: report text, failing tests (names, exceptions, stack traces), commit time/order, message, diff, files, size, author.
- `lambdamart` (learned): LightGBM LambdaMART (300 trees, 15 leaves) on the same features, retrained every 5 bugs. Inputs: report text, failing tests (names, exceptions, stack traces), commit time/order, message, diff, files, size, author.
- `heapdb` (heapdb): HeapDB, no feedback: exp. lag kernel (half-life 1y) x dose (diff size) x prior links (all equal). Inputs: report text, failing tests (names, exceptions, stack traces), commit time/order, message, diff, files, size, author.
- `heapdb+learned` (heapdb): HeapDB with prequential feedback (confirm the BIC, reject the other candidates); default config kernel=flat,dose=off,prior=0.001/10. Inputs: report text, failing tests (names, exceptions, stack traces), commit time/order, message, diff, files, size, author.
- `heapdb+learned+tuned` (heapdb): as heapdb+learned; kernel, dose and prior picked per bug by follow-the-leader over the fixed grid (best MRR on the bugs already seen). Inputs: report text, failing tests (names, exceptions, stack traces), commit time/order, message, diff, files, size, author.
- `heapdb+logistic` (heapdb): HeapDB, combine=logistic: link = sigmoid(b + sum of feature weights), weights learned online (FTRL-Proximal, L2 towards the prior seeds) from the same prequential feedback; default config combine=logistic,kernel=flat,dose=off,lr=0.1, prior Beta(1, 4). Inputs: report text, failing tests (names, exceptions, stack traces), commit time/order, message, diff, files, size, author.
- `heapdb+logistic+tuned` (heapdb): as heapdb+logistic; kernel, dose and learning rate (0.1, 0.5) picked per bug by follow-the-leader over the fixed grid. Inputs: report text, failing tests (names, exceptions, stack traces), commit time/order, message, diff, files, size, author.
- `abl:signal-buckets-only` (ablation): heapdb+learned with only the bucketed signals (no author/dir/keyword/component features). Inputs: report text, failing tests (names, exceptions, stack traces), commit time/order, message, diff, files, size, author.
- `abl:identity-only` (ablation): heapdb+learned with only author/dir/keyword/component features (no signal buckets). Inputs: report text, failing tests (names, exceptions, stack traces), commit time/order, message, diff, files, size, author.
- `heapdb+transfer` (transfer): heapdb+learned (default config) trained only on the other projects' bugs (leave one project out), no feedback from the held-out project. Inputs: report text, failing tests (names, exceptions, stack traces), commit time/order, message, diff, files, size, author.
- `logreg+transfer` (transfer): logistic regression (C=1) trained only on the other projects' bugs. Inputs: report text, failing tests (names, exceptions, stack traces), commit time/order, message, diff, files, size, author.
- `fonte` (published): FONTE (re-implemented): Ochiai rank votes, depth decay lambda=0.1, style changes removed (no report text). Inputs: FL scores, method history.
- `fl-max-aggregation` (published): max Ochiai score of the lines a commit evolved (FONTE's max-aggregation baseline). Inputs: FL scores, method history.
- `abl:fl-inputs-only` (ablation): heapdb+learned (default config) with only FONTE's inputs: FL vote rank, max Ochiai score and method-history depth buckets (no report, no text, no time). Inputs: FL scores, method history (FONTE's inputs) + feedback on earlier bugs.
- `same-author` (baseline): commits by the fix's author first, then newest. Inputs: authors.

Reading: multiplying the odds of the existing Beta links (naive Bayes with a learned base, the simplest option) is at or above noisy-OR on d4j/fl, dpdk/fixes and below it on d4j/report (by up to 0.071): naive Bayes counts correlated evidence (several buckets of related signals) once per feature. The online logistic regression, which learns discriminative weights, is at or above noisy-OR on d4j/fl, dpdk/fixes and below it on d4j/report (by up to 0.024), so the engine implements (c). Count credit beats the noisy-OR EM credit for the naive-Bayes variants, and an intercept seeded at a tiny base rate slows the online learner (its negative examples then have almost no gradient), which is why the logistic runs seed it with HeapDB's default prior Beta(1, 4).

### Why noisy-OR is at a disadvantage here

This was our reading of the first results; the logistic combine mode (above)
is the test. HeapDB's default link model is a noisy-OR over *causes*: each feature of an event is an
independent way of producing the effect, and the score adds up (in
probability) the strength of each feature. On this task most features are
not causes but *evidence* about one cause: a high BM25 rank, a file named in
the stack trace and a short lag all point at the same commit. Evidence
combines multiplicatively (as in logistic regression, which works in log
odds), while noisy-OR combines it roughly additively, so a candidate with
one very strong signal and a candidate with several weak ones end up close.
Bucketing continuous signals into binary features also discards the order
inside a bucket, which a model on the raw score keeps. The ablations point the
same way: the signal buckets carry almost all of HeapDB's accuracy, and the
identity features (author, directory, keyword) add little on their own.
The development-slice study shows the multiplication alone is not the whole
story: naive Bayes (odds of the existing Beta links multiplied together)
double-counts correlated buckets, and it is the discriminatively learned
weights of the online logistic regression that make the logistic mode work.

### Threats to validity

- **Labels.** Defects4J BICs come from Wen et al. (2019, test-based) and from
  manual curation by the FONTE authors (who restricted themselves to bugs with
  few candidate commits, an easier subset; see the provenance split). DPDK
  labels are developer-written `Fixes:` trailers; a trailer can name the wrong
  commit or only one of several.
- **Failure time.** Defects4J has no report timestamp in the artifact; the
  effect time is the newest candidate commit (the buggy revision or just
  before it). Lags are therefore lower bounds.
- **Leakage checks.** Methods rank before the label is revealed (tests assert
  that changing later labels never changes earlier ranks). Bug reports are
  the original issue texts; a handful mention a revision or commit (counted
  above). DPDK queries drop every trailer and hex id; a fix message can still
  quote the BIC's subject in prose (counted in the setup).
- **Equal inputs.** HeapDB and the learned baselines are built from the same
  signal table. They differ in learning schedule: HeapDB updates after every
  bug, logistic regression retrains after every bug on Defects4J but every
  500 bugs on DPDK, LambdaMART every 5 / 1000 bugs, and the DPDK learners
  keep 30 random negatives per bug (compute). This favours HeapDB slightly on
  DPDK.
- **Design on the data.** Bucket edges, the prior grid and the feature set
  were designed on the first quarter of each stream (development slice). That
  is a process claim; the split tables report both parts so a larger drop for
  HeapDB than for the baselines would be visible. The `abl:fl-inputs-only`
  row was added after the first full run, because the task called for an
  apples-to-apples row with FONTE's inputs; it uses the default
  configuration, with no tuning.
- **Learning curves drift.** The DPDK stream gets harder over time for every
  method; per-block MRR is comparable across methods, not across blocks.
- **Published systems.** Bug2Commit and FBL-BERT are their released per-bug
  outputs, re-scored on our candidate sets (the reproduction check confirms
  the re-scoring), not re-runs. FONTE is our re-implementation of its
  ICSE'23 configuration, checked against its released ranks.
- **Authors.** FONTE's commit files have no author; authors come from the
  upstream repositories (by commit id, or by unique timestamp for Lang and
  Math, whose Defects4J ids differ). Unmatched commits get author `?`.
